# Code Intelligence 面试问答文档

本文档用于帮助项目作者从面试者视角讲清楚 Code Intelligence 的价值定位、设计取舍、与 GitNexus 的关系，以及可能遇到的追问。

背景假设：

- 面试者希望通过 Code Intelligence 展示自己在 AI Agent 工程方面的能力。
- Code Intelligence 是一个本地代码情报工具，面向线上排障、代码理解、流程图生成、新人问答等上层 Agent。
- 当前第一版底层可以适配 GitNexus，同时也包含项目注册、Java 专项索引、轻量语义检索、grep 兜底、CLI 和 MCP 工具接口。
- 当前目标不是替代 GitNexus，而是为其他 Agent 提供稳定、结构化、可降级的代码证据底座。

## 1. 项目核心定位

### 问题：Code Intelligence 到底是什么？

推荐回答：

Code Intelligence 是一个面向 AI Agent 的本地代码情报底座。它把本地项目索引、结构化代码检索、GitNexus 能力适配、轻量语义检索、grep 兜底和诊断信息统一成 CLI 和 MCP 工具，让线上排障、流程图生成、新人问答等上层 Agent 能稳定获取可引用的代码证据。

它不是单纯的代码搜索工具，也不是要替代 GitNexus。它更像一个 Agent-facing 的代码证据接入层。

### 问题：为什么不要把它讲成“代码搜索工具”？

推荐回答：

因为“代码搜索”太普通，面试价值不够。普通 grep、IDE 搜索、GitNexus、向量库都能做不同形式的代码搜索。

这个项目更核心的价值是：

- 为 Agent 提供稳定工具接口。
- 将多种代码证据来源归一成统一结构。
- 支持索引状态诊断和降级。
- 让线上排障、流程图生成、新人问答等不同工具可以复用同一个代码证据底座。

所以它解决的不是“人怎么搜代码”，而是“AI Agent 如何可靠地获取代码上下文并基于证据推理”。

## 2. 与 GitNexus 的关系

### 问题：GitNexus 已经很强了，为什么不直接用 GitNexus？

推荐回答：

GitNexus 是强大的底层代码图谱和代码分析引擎，它提供上下文查询、调用链、影响分析、Git diff 影响分析、路由图、污点分析等能力。

但上层 Agent 的需求不是“直接面对一个复杂的底层工具集合”，而是“拿到稳定、结构化、可诊断、可降级的代码证据”。

比如线上排障 Agent 输入的是日志、错误码、接口路径、SQL 片段。它希望快速知道：

- 这段日志最可能对应哪些代码位置？
- 这个接口路径对应哪个 Controller 方法？
- 这个错误码在哪里定义和抛出？
- 这条 SQL 或表名对应哪个 Mapper？
- 当前索引是否过期？
- 结果来自 GitNexus、Java 索引、语义索引，还是 grep 兜底？

如果每个上层工具都直接接 GitNexus，就会重复处理能力选择、输出解析、错误降级、业务场景适配和结果归一。

Code Intelligence 的定位是把这些公共能力收拢成一个统一的 Agent 接入层。

一句话总结：

> GitNexus 是底层分析引擎，Code Intelligence 是面向上层 Agent 的代码证据协议和场景编排层。

### 问题：这是不是 GitNexus 套壳？

推荐回答：

不是简单套壳，但也不应该否认它复用了 GitNexus 的底层能力。

更准确地说，Code Intelligence 是在 GitNexus 这类底层代码分析能力之上，做了一层面向 Agent 的适配和产品化封装。

它的核心价值不在于重做 GitNexus 的全部图谱能力，而在于：

- 提供稳定的 MCP 和 CLI 调用入口。
- 把不同来源的代码证据统一成 `SearchResponse`。
- 为 Java Spring MyBatis 场景补充专项索引。
- 暴露索引状态、降级状态和诊断信息。
- 让线上排障、流程图、新人问答等上层工具不直接耦合 GitNexus。

面试时可以这样说：

> 如果只看底层代码分析能力，GitNexus 更强；但如果看 AI Agent 工具链落地，Code Intelligence 解决的是“怎么把代码分析能力稳定、安全、可组合地暴露给多个 Agent”的问题。

### 问题：使用 Code Intelligence 是否等于舍弃 GitNexus 的高级能力？

推荐回答：

当前第一版确实没有完整接入 GitNexus 的全部高级能力，例如爆炸半径分析、Git diff 影响分析、完整语义检索和 PDG 相关能力。这是阶段性取舍，不是架构上舍弃。

第一版优先打通最小闭环：

- 本地项目注册。
- 项目索引。
- Java 场景索引。
- 统一搜索。
- 代码定位。
- 索引诊断。
- grep 兜底。
- CLI 接入。
- MCP 接入。

在这个闭环稳定之后，GitNexus 的高级能力可以继续接入：

- 爆炸半径分析可以映射为 `CodeRelation` 或影响证据。
- Git diff 影响分析可以扩展为 `code.analyze_change` 工具。
- 调用链分析可以补充到 `relations` 字段。
- 语义检索可以作为新的搜索来源。
- 路由图和 API 影响分析可以服务流程图生成和接口变更风险评估。

所以正确说法是：

> 当前版本没有完全利用 GitNexus 的高级能力，但架构上保留了接入空间。第一版先做 Agent 可依赖的统一接口契约，第二阶段再增强底层图谱能力。

### 问题：为什么不直接让线上排障 Skill 调 GitNexus？

推荐回答：

因为 Code Intelligence 是通用底座，不是线上排障 Skill 的内部模块。

线上排障 Skill 只是其中一个调用方。未来还可能有：

- 流程图生成工具。
- 新人代码问答工具。
- PRD 详设辅助工具。
- 变更影响分析工具。
- 代码 Review 辅助工具。

如果线上排障 Skill 直接耦合 GitNexus，那么后续每个工具都要重新适配 GitNexus 的工具接口和输出格式。

Code Intelligence 的设计是让上层工具只适配统一协议。底层是 GitNexus、Java 索引、向量库、grep，还是未来其他代码图谱引擎，都不应该影响上层工具。

这体现的是工程中的解耦能力。

## 3. 面试推荐表达

### 30 秒版本

推荐回答：

Code Intelligence 不是为了替代 GitNexus。GitNexus 是底层代码分析引擎，而我做的是面向 AI Agent 的代码情报接入层。

线上排障、流程图生成、新人问答这些 Agent 不应该直接面对复杂的底层图谱工具，而应该调用一个稳定、结构化、可降级的代码证据接口。

所以 Code Intelligence 做的是项目注册、索引编排、Java 场景索引、GitNexus 适配、grep 兜底、诊断信息和统一输出协议。第一版没有完整接入 GitNexus 的所有高级能力，这是取舍；后续可以把影响分析、变更分析、语义检索逐步接入统一模型。

### 2 分钟版本

推荐回答：

我做这个项目时，真正想解决的不是“代码搜索”本身，而是 AI Agent 如何可靠地获取代码上下文。

直接用 GitNexus 当然可以，它能力很强，包括调用图、影响分析、变更影响、路由图等。但问题是，上层 Agent 的需求不是“调用一个强大的工具”，而是“拿到一份结构化、可引用、可诊断、可降级的代码证据”。

比如线上排障 Agent 输入的是日志、错误码、接口路径、SQL 片段，它需要快速定位到 Controller、Service、Mapper、异常抛出处，并知道这些证据来自哪里、索引是否过期、有没有降级。流程图工具则需要从入口代码出发，抽取业务链路。新人问答工具需要把业务词转换成代码证据。

所以我把 Code Intelligence 定位成一个 Agent-facing 的代码情报层。它通过 CLI 和 MCP 暴露统一接口，内部可以使用 Java 专项索引、轻量语义检索、grep 兜底，也可以适配 GitNexus。这样其他工具接入时只依赖统一协议，而不是直接耦合 GitNexus 的每个能力和输出格式。

当前第一版确实没有覆盖 GitNexus 的全部高级能力，这是我刻意控制范围：先把注册、索引、搜索、定位、诊断、MCP 调用链路跑通，再逐步把 GitNexus 的影响分析、Git diff 分析、调用链分析接入成统一证据模型的一部分。

## 4. 项目体现的 AI Agent 能力

### 问题：这个项目怎么体现 AI Agent 工程能力？

推荐回答：

这个项目体现的不是简单调模型，而是 AI Agent 工程里的几个关键能力。

第一，工具协议设计能力。

Code Intelligence 把代码检索能力设计成 CLI 和 MCP 工具，例如 `code.search`、`code.locate_route`、`code.index_project`。这说明我考虑的是如何让其他 Agent 稳定调用，而不是只做一个人手动使用的脚本。

第二，上下文工程能力。

Agent 不能无限读取整个代码仓库。Code Intelligence 的作用是把代码仓库压缩成结构化证据，让 Agent 按需拿到相关代码位置、证据来源和诊断信息。

第三，证据归一能力。

不同来源的检索结果最终统一成同一种结果结构。这样线上排障、流程图、新人问答工具都可以复用同一套协议。

第四，降级与诊断能力。

底层索引可能不可用，GitNexus 可能不可用，索引可能过期。Code Intelligence 不会隐藏这些问题，而是通过诊断信息告诉上层 Agent 当前证据是否可靠、是否发生降级。

第五，可扩展的编排能力。

当前可以接 Java 索引和 GitNexus，未来可以接向量库、知识库、链路追踪、日志平台、PR diff 影响分析等能力。统一接口不变，上层工具不用大改。

## 5. 面试高频问题与回答

### 问题 1：你这个项目到底解决什么问题？

推荐回答：

它解决的是 AI Agent 如何可靠获取代码证据的问题，而不是单纯解决代码搜索。

线上排障、流程图生成、新人问答这些 Agent 都需要理解代码，但它们不应该每次都从零读完整仓库。Code Intelligence 提供一个统一入口，把接口、日志、错误码、SQL、业务关键词等线索转换成可引用的代码位置和证据。

### 问题 2：为什么不用 grep？

推荐回答：

grep 只能做文本匹配，不能理解结构，也不能表达证据可靠性。

比如线上日志里有一个接口路径，grep 可以搜到文本，但它不知道这是 Controller 路由、Mapper SQL、错误码定义，还是普通字符串。它也不会告诉 Agent 当前索引是否过期、是否有降级、结果来源是什么。

Code Intelligence 可以把 grep 作为兜底，但不能只依赖 grep。

### 问题 3：为什么不直接做 RAG？

推荐回答：

代码场景不能只靠向量相似度。

接口路径、方法签名、错误码、SQL、日志文本这些线索，很多时候需要精确匹配和结构化索引。RAG 可以作为召回手段之一，但如果只做向量化，很容易召回语义相似但实际无关的代码。

所以我的设计是混合检索：

- 结构化索引用于接口、SQL、错误码、日志等明确线索。
- 轻量语义检索用于业务词和自然语言查询。
- grep 用于兜底。
- GitNexus 用于更深层的代码图谱和影响分析。

### 问题 4：为什么要有 MCP？

推荐回答：

因为 MCP 是面向 Agent 的工具协议。CLI 适合人和脚本使用，MCP 适合让 AI Agent 调用。

如果这个项目只提供命令行，那么上层 Agent 需要自己拼命令、解析输出、处理错误。MCP 可以把能力暴露成结构化工具，让 Agent 更稳定地调用。

### 问题 5：为什么要同时提供 CLI 和 MCP？

推荐回答：

CLI 和 MCP 面向不同调用方。

CLI 适合开发者本地调试、手动索引、脚本集成。MCP 适合线上排障 Agent、流程图 Agent、新人问答 Agent 等自动调用。

两者共用 core 能力，避免重复实现。

### 问题 6：为什么要拆成 core、CLI、MCP？

推荐回答：

core 放核心领域能力，例如项目注册、索引、搜索路由、诊断和数据模型。

CLI 是人和脚本的入口。

MCP 是 Agent 的入口。

这样拆分后，核心能力可测试、可复用，上层入口也可以独立演进。

### 问题 7：为什么要设计统一的 `SearchResponse`？

推荐回答：

因为上层 Agent 需要稳定的数据结构。

如果 GitNexus、Java 索引、语义检索、grep 兜底都返回不同格式，那么每个上层工具都要重复适配。

统一的 `SearchResponse` 可以表达：

- 查询内容。
- 匹配结果。
- 代码位置。
- 证据来源。
- 诊断信息。
- 降级状态。
- 未来的调用关系或影响关系。

这让上层 Agent 可以基于同一套结构继续推理。

### 问题 8：为什么 `Diagnostic` 很重要？

推荐回答：

因为 Agent 需要知道结果是否可靠。

如果索引过期、GitNexus 不可用、只用了 grep 兜底，而工具没有告诉 Agent，Agent 可能会基于不完整证据输出错误结论。

`Diagnostic` 的价值是把工具状态显式暴露出来，让上层 Agent 可以决定：

- 是否继续追查。
- 是否补充搜索。
- 是否提示用户结果置信度有限。
- 是否建议重新索引。

这体现的是 Agent 工具的可观测性。

### 问题 9：为什么需要 grep 兜底？

推荐回答：

因为底层索引不一定永远可用。

GitNexus 可能没安装，索引可能缺失，项目可能刚注册还没完整索引。这个时候工具不能直接不可用。grep 兜底可以提供最低限度的代码证据。

但 grep 结果必须被标记为兜底来源，不能伪装成高置信度结构化结果。

### 问题 10：Java 专项索引有什么价值？

推荐回答：

第一版优先支持 Java Spring MyBatis，是因为线上排障场景非常明确。

Java 后端排障经常从这些线索进入：

- 接口路径。
- Controller 方法。
- Service 调用。
- Mapper SQL。
- 表名。
- 错误码。
- 异常。
- 日志关键字。

这些线索用结构化索引比纯语义检索更可靠。

### 问题 11：如果 GitNexus 不可用怎么办？

推荐回答：

Code Intelligence 不会让上层 Agent 直接失败。它会降级到本地 Java 专项索引、轻量语义索引或 grep，并通过诊断信息说明 GitNexus 不可用。

这种设计的目标不是掩盖失败，而是让上层 Agent 明确知道当前结果的能力边界。

### 问题 12：当前最大短板是什么？

推荐回答：

当前最大短板是当前版本已经能返回代码位置、邻域关系边和两点 trace，但还没有把“从一个线索自动探索上下游调用链”做成足够自然的高层能力。

比如用户只知道一个错误码、日志、SQL、方法名或业务词时，当前需要先 search 找 anchor，再看 relations，再用 trace 验证路径。这个过程对 Agent 可用，但对人直接使用还不够顺手。

所以下一步应该补 `explore_symbol`、`find_callers`、`find_callees`、`find_entry_paths` 这类单点探索能力，并继续接入 GitNexus 的影响分析、Git diff 分析和更强图查询能力。

### 问题 13：如果 `trace` 返回空 path，能不能说明代码里没有调用链？

推荐回答：

不能。空 path 只能说明当前工具没有生成可用路径证据，不能说明真实代码或运行时一定没有调用关系。

空 path 可能有很多原因：

- 符号没找到。
- 符号有多个候选，需要 UID 或文件路径消歧。
- 两个符号都找到了，但静态图谱没有发现有向路径。
- depth 太小或结果被 limit 截断。
- 动态派发、反射、Spring AOP、MQ、RPC、定时任务等边界没有被静态图谱完整串起来。
- GitNexus 不可用、索引缺失或索引过期。

因此工具不能把空 path 解释成“确认没有调用链”，而应该通过 `diagnostics` 告诉上层 Agent 原因和下一步建议。

我会把结果分成四个证据等级：

- 有 `paths` 或 trace relations：可以说“发现候选调用路径”。
- 没有 path，但有 `relations`：只能说“发现相关代码关系，但未形成完整路径”。
- 没有 relations，但有 `locations`：只能说“定位到代码位置，关系能力降级”。
- 没有 locations：说明没有足够代码证据，需要补充 query 或重新索引。

对上层 Agent 来说，最重要的是不要幻觉。没有 path 时，Agent 应该降级为候选分析、要求消歧、尝试扩大 depth、切换方向、查看邻域 context，或者结合线上 trace/log 验证运行时链路，而不是编造调用链。

这体现了 Agent 工具设计里的一个核心原则：

> 工具不只是返回答案，更要告诉 Agent 当前证据能支持什么结论，不能支持什么结论。

### 问题 14：你下一步会怎么演进？

推荐回答：

我会优先做四件事：

1. 做 `explore_symbol`，从一个错误码、日志、SQL、方法名或业务词出发，自动定位 anchor 并展开 upstream/downstream 候选路径。
2. 深度接入 GitNexus 的影响分析和调用链能力，把结果映射到统一的 `relations`、`paths` 或影响证据模型。
3. 增加 `code.analyze_change`，支持 Git diff 影响分析，辅助代码 Review 和上线风险评估。
4. 建立评测集，用真实日志、接口路径、错误码、SQL 片段验证检索准确率和根因定位帮助程度。

1. GitNexus 已经有很多能力，你为什么还要做一层？

### Agent 工程类

## 7. 建议背诵的关键句

1. Code Intelligence 不是替代 GitNexus，而是面向 AI Agent 的代码情报接入层。

2. GitNexus 更像底层代码图谱引擎，Code Intelligence 更像上层 Agent 可稳定调用的代码证据协议。

3. 我解决的不是“人怎么搜代码”，而是“Agent 如何可靠获取代码上下文并基于证据推理”。

4. 直接把 GitNexus 暴露给每个 Agent，会带来能力选择、输出解析、降级策略和业务适配的重复复杂度。

5. 第一版没有完整接入 GitNexus 的高级能力，这是阶段性取舍，不是架构限制。

6. 对 AI Agent 来说，工具失败不可怕，可怕的是失败被隐藏，所以诊断信息必须是一等公民。

7. grep 可以作为兜底，但不能作为核心能力，因为它不能表达代码结构和证据可靠性。

8. RAG 可以作为召回来源之一，但代码理解不能只靠向量相似度，结构化索引仍然很重要。

9. 这个工具的价值是把接口、日志、错误码、SQL、业务词这些线索转换成可引用的代码证据。

10. 后续演进方向是把 GitNexus 的影响分析、变更分析、调用链分析接入统一证据模型。

## 8. 自测题

### 自测题 1：如果面试官说“这就是 GitNexus 套壳”，你怎么回答？

参考回答：

我会承认 GitNexus 的底层代码分析能力更强，也承认我的工具复用了它的能力。但 Code Intelligence 的目标不是替代 GitNexus，而是做面向 AI Agent 的接入层。

上层 Agent 需要的是稳定、结构化、可诊断、可降级的代码证据，而不是直接面对一组复杂的底层图谱工具。Code Intelligence 把 GitNexus、Java 专项索引、语义检索和 grep 兜底统一成一个协议，让线上排障、流程图、新人问答等工具都能复用。

所以它不是简单套壳，而是 Agent 工程里的适配层、证据归一层和场景编排层。

### 自测题 2：线上排障 Agent 最小需要哪几类代码证据？

参考回答：

至少需要这些证据：

- 日志关键字对应的代码位置。
- 异常类和错误码定义位置。
- 接口路径对应的 Controller 方法。
- 相关 Service 和 Mapper 入口。
- SQL、表名、Mapper 方法。
- 证据来源和索引状态。
- 是否发生降级。

这些证据可以帮助排障 Agent 从线上日志反推到代码实现，再结合日志和链路信息判断根因。

### 自测题 3：`SearchResponse` 里哪个字段最能体现 Agent 工程能力？

参考回答：

我认为 `diagnostics` 和 `evidence` 最能体现 Agent 工程能力。

`evidence` 让 Agent 的结论有出处，不是纯自然语言猜测。

`diagnostics` 让 Agent 知道工具当前是否可靠，是否发生降级，索引是否过期。这能防止 Agent 在证据不足时输出过度确定的结论。

### 自测题 4：为什么 `Diagnostic` 不是可有可无的字段？

参考回答：

因为 Agent 调用工具时，不只需要结果，也需要知道结果是否可信。

如果只返回代码位置，不返回索引状态和降级信息，Agent 就无法判断这个结果是来自结构化索引、GitNexus、语义检索，还是 grep 兜底。

这会导致 Agent 把低置信度结果当成确定结论。`Diagnostic` 的作用就是让不确定性显式化。

### 自测题 5：索引缺失、索引过期、部分可用，分别应该如何影响 Agent 的回答？

参考回答：

索引缺失时，Agent 应该提示需要先索引，或者使用 grep 兜底，并明确结果置信度较低。

索引过期时，Agent 可以返回已有结果，但要提示代码可能已经变化，建议重新索引。

部分可用时，Agent 应该说明哪些索引可用、哪些索引不可用，例如路由索引可用但 GitNexus 图谱不可用。

这类状态会直接影响 Agent 的结论置信度和下一步行动。

### 自测题 6：GitNexus 的爆炸半径分析接入后，应该映射到哪个输出结构？

参考回答：

可以映射到 `relations` 或单独的影响证据结构。

比如某个方法变更后，GitNexus 返回受影响的调用方、接口、测试、模块。Code Intelligence 可以把这些结果转换成统一的代码关系或影响证据，并保留 `source=gitnexus`。

这样上层 Agent 不需要理解 GitNexus 原始输出，只需要消费统一模型。

### 自测题 7：什么时候用结构化索引，什么时候用语义检索，什么时候用 grep 兜底？

参考回答：

明确线索优先用结构化索引，例如接口路径、HTTP 方法、错误码、日志文本、SQL、表名、Mapper。

业务词、自然语言描述、功能名称可以用语义检索辅助召回。

当结构化索引和语义检索不可用，或者需要最后兜底时，再使用 grep。

这三个能力不是互相替代，而是按可靠性和场景分层使用。

### 自测题 8：这个项目第一版最大的工程取舍是什么？

参考回答：

最大的取舍是第一版没有追求完整代码图谱和完整 RAG 问答，而是先做可落地的 Agent 工具闭环。

也就是先完成项目注册、索引、搜索、代码定位、诊断、降级、CLI 和 MCP 接入。

这个取舍是合理的，因为如果没有稳定的工具协议和证据模型，直接堆高级能力会让上层 Agent 更难使用。先建立可靠接口，再接入 GitNexus 的高级能力，是更稳的演进路线。

### 自测题 9：如果调用链查询返回空 path，Agent 应该怎么处理？

参考回答：

空 path 不能解释成“确认没有调用关系”。它只说明当前工具没有生成可用路径证据。

可能原因包括：

- 符号没找到。
- 符号有歧义，需要 UID 或文件路径消歧。
- 静态图谱没有发现有向路径。
- depth 太小或结果被 limit 截断。
- 动态派发、反射、Spring AOP、MQ、RPC、定时任务等运行时边界没有被静态图谱完整表达。
- GitNexus 不可用、索引缺失或索引过期。

Agent 应该按证据等级降级：

- 有 path 或 trace relations：可以说发现候选调用路径。
- 没有 path，但有 relations：只能说发现相关代码关系，未形成完整路径。
- 没有 relations，但有 locations：只能说定位到代码位置，关系能力降级。
- 没有 locations：说明没有足够代码证据，需要补充 query 或重新索引。

因此，空 path 时 Agent 应该查看 `diagnostics`，再决定是要求消歧、扩大 depth、切换 upstream/downstream、查看邻域 context，还是结合线上 trace/log 验证运行时链路。不能为了完成回答而编造调用链。

一句话总结：

> 工具不只是返回答案，更要告诉 Agent 当前证据能支持什么结论，不能支持什么结论。

## 9. 面试表达注意事项

### 应该主动承认的点

- GitNexus 的底层代码分析能力比当前第一版更强。
- 当前版本还没有完整接入 GitNexus 的高级能力。
- 当前更偏代码定位和证据归一，不是完整业务理解系统。
- 当前主要面向本地已克隆目录，不支持 GitLab 远程仓库索引。
- 当前主要聚焦 Java Spring MyBatis 场景。

主动承认这些点不会减分，反而会显得判断清楚。

### 不建议这样说

不要说：

- 我做了一个比 GitNexus 更强的工具。
- 我的工具可以替代 GitNexus。
- 只要输入日志就一定能自动定位根因。
- RAG 可以完全解决代码理解。
- grep 足够解决代码检索。

这些说法容易被追问击穿。

### 建议这样说

建议说：

- 我没有重复造 GitNexus，而是做 Agent 接入层。
- 我第一版优先解决稳定工具契约和端到端闭环。
- 高级代码图谱能力可以通过 GitNexus 逐步接入。
- 这个工具强调可引用证据、诊断信息和降级策略。
- 它的价值是让多个上层 Agent 共享同一个代码证据底座。

## 12. v0.4 主链路能力面试材料

v0.4 的重点从“候选路径探索”推进到“主链路证据生成”。相关设计和面试素材已拆到两份独立文档，准备模拟面试前建议重点阅读：

- `docs/2026-08-21-code-intelligence-main-path-v04-design.zh-CN.md`：v0.4 `main_paths` 设计规格，包括输出契约、coverage、budget_summary、评分体系、折叠策略和验收标准。
- `docs/2026-08-21-code-intelligence-v04-main-path-interview-prep.zh-CN.md`：v0.4 面试讲解素材，包括为什么暂不接 JDT LS、关系边爆炸如何处理、剪枝如何避免误导、评分体系如何自证合理。

这一阶段面试表达的核心句子：

> v0.4 不是把 GitNexus 关系边简单包装给 LLM，而是把图谱邻域关系转化成 Agent 可消费的主链路候选；同时用 coverage、budget_summary 和 diagnostics 明确告诉上游 Agent 结果是预算内证据子集，不是完整项目图谱。

### 12.1 问：输出模型这么复杂，上游 Agent 怎么理解？

答：

不能靠上游 Agent 自己猜。V0.4 专门把输出拆成两层：

- 主消费层：`main_paths`、`coverage`、`diagnostics`、`summary`
- 证据审计层：`anchors`、`relations`、`side_relations`、`candidate_paths`、`budget_summary`

上游 Agent 默认只看主消费层。`main_paths` 告诉它优先验证哪条主链路，`coverage` 告诉它能不能声明完整，`diagnostics` 告诉它是否需要提高预算、缩小 query 或继续二次 explore。

我还补了一份字段契约文档：`docs/2026-08-21-code-intelligence-v04-output-contract.zh-CN.md`。这份文档明确写了哪些字段可以作为结论依据，哪些字段只能作为线索，`coverage.complete=false` 时应该怎么表述。也就是说，复杂字段不是暴露给 Agent 自由发挥，而是通过契约约束 Agent 的消费方式。

### 12.2 问：`relations` 被预算裁剪后，上游 Agent 会不会被误导？

答：

会，所以 V0.4 明确不把 `relations` 定义为完整图谱，而定义为“预算内证据子集”。上游 Agent 不能说“没在 relations 里就是不存在”，只能说“本次预算内没有返回该关系”。

真正给上游 Agent 做初步判断的是 `main_paths`。`main_paths` 是在预算内关系证据上经过主链路优先级、角色识别、评分和折叠得到的候选路径。它仍然不是完整运行时调用链，但比直接读一堆关系边更适合排障和业务理解。

### 12.3 问：V0.4 生产价值在哪里？

答：

它解决的是 Agent 工具最容易出问题的地方：不是查不到代码，而是查到太多关系后主次不清。线上排障 Agent 或流程图 Skill 不应该自己从 imports、test、has_method、calls 混杂的关系边里猜主链路。V0.4 先给出 `main_paths`，再把辅助证据放到 `side_relations`，同时用 `coverage` 告诉 Agent 结果是否完整。

这样上游 Agent 可以先沿主链路定位核心业务，再围绕主链路节点继续展开细节，成本更低，结论也更可控。
